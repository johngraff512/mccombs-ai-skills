## Architecture (read before editing)

`ARCHITECTURE.md` holds the long-form version of this section; keep the two in step when structure changes.

- `plugins/<name>/skills/<skill>/` — installable skills. For most plugins this is the source of truth. **Exception:** `plugins/mccombs-case-toolkit/` is BUILT OUTPUT — never edit it directly.
- `artifacts/<name>/` — interactive HTML tools (Claude artifacts, e.g. Cowork chat apps), each with the .html file plus an `artifact.json` manifest (name, title, summary, description, `category` (same vocabulary as skills; defaults to General), version, file, platform, author, optional `link` to a published/shared artifact URL). Not validated by check_skills.py and not zipped into releases — build_catalog.py copies the .html into `docs/artifacts/files/` for direct download and renders an "Artifacts" catalog section + detail page. The detail page offers two ways in and `link` drives which: when set, "Open it in your browser" (the shared claude.ai artifact) renders first and open, and "Add it to your own AI app" (download the .html, attach it to a Claude conversation, ask for it as an artifact, then bookmark or Fork) is the second, collapsed option; with no `link` the download path is the only one and opens by default. The Option C row surfaces both the same way. Set `platform` to "Claude" — these open from claude.ai or the Claude app, not Cowork specifically. Every artifact detail page carries a "Good to know" note that the chat only works inside Claude's artifact runtime, because the page reaches the Anthropic API through Claude's own bridge; opening the raw .html in a normal browser renders the interface but can't send messages. They don't work in ChatGPT.
- `toolkits/mccombs-case-toolkit/` — canonical source for the case toolkit: `src/skills/` + `src/shared/` (shared resources injected per-skill at build time via `toolkit.json`), `platforms/` overlays (ChatGPT yaml, Claude plugin.json), own `scripts/build.py` and `scripts/validate.py`. After editing source: `python3 toolkits/mccombs-case-toolkit/scripts/build.py --clean --target claude`, copy `build/claude/skills` over `plugins/mccombs-case-toolkit/skills`, commit both. CI has a drift check that fails if they diverge.
- `scripts/check_skills.py` — spec validator + platform classifier. Classifications: `both`, `both-with-caveats`, `claude-code-only` (badge: "Needs local software"; triggered by allowed-tools containing `Bash(`), `claude-only` (MCP/local-Claude deps, or a browser-extension dependency — see below). Signals must stay in plain faculty-facing language.
  - The two Canvas skills drive the Canvas REST API from inside an authenticated Chrome tab via the **Claude for Chrome** extension, which ChatGPT has no equivalent of, so they classify `claude-only` and the catalog shows "Not available" for ChatGPT rather than an install path that cannot work. The `CLAUDE_ONLY_PATTERNS` entry matching this is deliberately narrow (`Claude for/in Chrome`, `browser extension`) — a bare mention of "browser" must not trip it, or beamer and the case toolkit get misclassified.
- `scripts/package_skills.py` — per-skill zips + `<plugin>-plugin.zip` bundles into `dist/` (gitignored).
- `scripts/build_catalog.py` — generates `docs/index.html` + per-skill pages (`docs/skills/`) + toolkit pages (`docs/toolkits/`) from `docs/compat-report.json`. Also generates **`docs/option-c.html`**, a dense filterable-index prototype running alongside the live catalog for faculty feedback (`catalog_entries()` flattens skills + plug-ins + artifacts into one row model; `option_c_page()` renders it; both pages share `CSS`/`page_shell` so they can't drift). The prototype links to the same detail pages, and the live catalog links to it from the footer ("Preview a new layout"). To retire it, delete `option_c_page()`, its `main()` call, and that footer link. Also generates **`docs/start-here.html`** (`start_here_page()`), the plain-English guide for faculty new to skills. **All user-facing explanation lives in the `GLOSSARY` and `BADGE_HELP` dicts** — the intro strip, every tooltip, and the Start Here page render from them, so edit the copy there and it updates everywhere at once. Every page includes `JS_HELP` (tooltips, copy buttons, intro-strip dismissal via `localStorage`); `tooltip()` builds accessible hint buttons whose position is clamped into the viewport at runtime. A plugin gets a "Plug-in" card only if `toolkits/<name>/` exists. Faculty-facing terminology: "Plug-in (for Claude only)" — plug-ins work on claude.ai web, desktop, Cowork, and Claude Code (verified: support.claude.com/en/articles/13837440); ChatGPT has no plug-ins.
- `.github/workflows/validate.yml` — PR/push: validate → drift check → package → catalog (committed back on master by CI). Tags `v*`: release with all zips including toolkit platform bundles built from source.
- Every repo/release/CONTRIBUTING link in the catalog is built from `REPO_URL`, which is `$GITHUB_SERVER_URL` + `$GITHUB_REPOSITORY` (Actions sets both on github.com *and* on GitHub Enterprise Server), falling back to `https://github.com/johngraff512/mccombs-ai-skills` locally. Don't hardcode the host — a build on UT's GHES must emit `github.austin.utexas.edu` links, and hardcoding silently produces dead links pointing at a public repo that doesn't exist.

## Conventions

- Frontmatter: spec fields only (`name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`). Every skill should carry `metadata.category` (one of: Case Writing, Class Preparation, Course Administration, Slides & Presentations, Research & Summaries, Decision Support, General — keep this list in step with `CATEGORY_ORDER` in build_catalog.py; an unlisted category still renders but sorts last), `metadata.version` — bump version on every content change; the catalog surfaces it to faculty — `metadata.summary`: one plain-English sentence (<200 chars) shown on catalog cards; without it the catalog falls back to truncating the description, which reads poorly — and `metadata.examples`: 2-3 realistic prompts (each <200 chars) rendered as the "Try saying…" panel, which is how faculty learn that skills trigger from ordinary requests rather than a command. The validator warns when either is missing.
- No `../` references escaping a skill folder (packager bundles them as a workaround, but fix at source; case toolkit solves this via build-time injection).
- Contributor flow: PR (web upload path documented in CONTRIBUTING.md for non-Git faculty) → CI checks → maintainer merge → tag release. Contact: john.graff@mccombs.utexas.edu.
- `business-ai-tools` skills are adapted from Ben Bentzin's MIT repo (github.com/AI-Business-Tools/claude-code) — keep attribution; upstream sync is manual. Known upstream issues we fixed locally: beamer YAML quoting + description length.

## Release checklist

1. `python3 scripts/check_skills.py --strict --json docs/compat-report.json`
2. If toolkit source changed: rebuild (see above) and verify drift check passes locally: `diff -r toolkits/mccombs-case-toolkit/build/claude/skills plugins/mccombs-case-toolkit/skills`
3. `python3 scripts/build_catalog.py` and eyeball `docs/index.html` — requires the `markdown` package (CI installs it; without it every detail page silently degrades to `<pre>` rendering). Add `--strict` (as CI does) to fail rather than publish a guessed per-skill "updated" date; a genuinely uncommitted skill prints a "no commits yet" note and is not an error.
4. Update CHANGELOG.md; commit; push; `git tag v0.x.y && git push --tags`
5. Verify: Actions green, release assets present, catalog live at https://johngraff512.github.io/mccombs-ai-skills/ (CI regenerates `docs/` and commits it back to master itself, so source-only PRs are expected — revert local `docs/` changes before committing)
